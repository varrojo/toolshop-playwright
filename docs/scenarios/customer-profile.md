# Customer Profile — Scenario Plan

[← Back to README](../../README.md#scenarios-covered-per-module)

Status: 🟡 In progress — 21 of 27 scenarios done.

Source: site's Testing Guide, feature #4 (Customer Profile).

**Acceptance Criteria**

- First name, last name, phone, address fields can be updated.
- Password reset cannot reuse the current password.
- After password reset, user is logged out automatically.

**Techniques applied:** Equivalence Partitioning (valid vs. invalid phone, postal code), State Transition Testing (session state after password reset), Boundary Value Analysis (field length max, e.g. 40 chars for city).

**Out of scope:** the Profile page also has a "Set up Two-Factor Authentication" section (QR code, manual key, `totp-code`/`verify-totp`) below the Password form — not covered by this module's AC. Would need its own AC/testing guidance before scoping scenarios for it.

## Test account strategy

Password-change scenarios mutate the account's actual credential, so each one needs its own disposable, freshly-registered user (same pattern as `login.md`'s lockout-adjacent scenarios) — reusing one account across parallel password-reset tests would leave later tests unable to log in with the password they expect. Field-update scenarios (name/phone/address) don't mutate credentials and can share a single `registeredUser`-style fixture per test.

Confirmed live: the Profile page's fields/validators take a moment to finish loading after navigation — submitting immediately after arriving on `/account/profile` can show "Please correct the highlighted fields before saving." even with valid data in every field. The POM's navigation/goto step should wait for the form to be genuinely interactive (e.g. wait for a populated field value, not just element visibility) before any test fills it in.

Confirmed live (a real trap hit while verifying #18-25 below): chaining many blank/submit/restore cycles back-to-back on **one** page instance produces inconsistent, unreliable results — later iterations in a loop stopped firing any request or showing any banner at all, even though the same blank-field submission reliably failed when tested in isolation on a fresh account. Each blank-field scenario needs its own fresh `registeredUser` and its own fresh navigation to `/account/profile` — don't loop multiple field-blanking assertions against the same page load.

Real cross-browser bug found while implementing #1-8: all 8 passed on Chromium but **all 8 failed on Firefox** — not flaky, consistently. Root cause: the Profile form's validity state is shared with the page's Two-Factor Authentication section (see "Out of scope" above), which fires its own async `GET /totp/setup` call to generate the QR code. `waitUntilLoaded()`'s original check (wait for `first-name` to have a value) doesn't wait for that TOTP fetch to finish — Chromium is fast enough that it usually finishes anyway, Firefox isn't, so submitting mid-race triggers the same "Please correct the highlighted fields" false-invalid banner, and no PUT request fires. Fixed by adding `await this.page.waitForLoadState('networkidle');` to `waitUntilLoaded()` — confirmed 24/24 passing across Chromium/Firefox/WebKit after the fix.

## Issues Found

### Issue #1 — Phone field validation rules don't match Registration's

The Profile page's phone field doesn't follow the same validation rules or accepted formats as Registration's phone field, even though both are meant to hold the same kind of data:

- **Register** (`register.md` #19/#32): rejects anything that isn't a digit — `+`, letters, and other symbols all trigger "Only numbers are allowed."
- **Profile** (#10 above): accepts `+`, `-`, spaces, and `()` alongside digits (e.g. `-123456` is valid), and only rejects letters/other symbols, with a different message ("Please enter a valid phone number (digits, spaces and ( ) + - only).").

So a phone number format that Register would reject outright can be successfully saved on Profile, and vice versa depending on the exact characters used. This is the kind of drift that typically happens when the same conceptual field is validated independently in two different forms rather than sharing one validation rule — worth flagging as an inconsistency regardless of whether either individual rule is "correct" on its own.
